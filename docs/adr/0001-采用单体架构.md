# ADR-0001：采用单体架构（Spring Boot 单应用 + MySQL + Redis，RabbitMQ 可选）

- 状态：已采纳（补记，2026-09-29；实际决策于 2025-11 开发期间做出）
- 决策人：格桑

## 背景

- 规模：日喀则分公司 14 个仓库、约 400 名员工；一天几十到几百张申请，不存在需要单独扩容的热点模块
- 团队：1 人开发、1 人运维（同一个人），没有运维平台，部署目标是一台机器上的 docker-compose
- 核心业务"审批通过"一步要同时完成：改申请单状态、锁定多种物资的库存、生成出库单、写库存流水——**这些必须一起成功或一起失败**（见 [ADR-0002](0002-出库分两步-审批锁定-取货扣减.md)）

## 决策

一个 Spring Boot 应用，按 controller / service / mapper 分层，按业务分包（申请、出库、入库、库存、统计、消息）。

| 组件 | 用途 | 挂了会怎样 |
|---|---|---|
| MySQL | 唯一的事实来源；库存的并发控制靠行锁 + 版本号 | 系统不可用 |
| Redis | 登录失败计数、令牌黑名单、定时任务的分布式锁（`wms:lock:*`） | 登录防护 **fail-closed**（拒绝登录而不是放行） |
| RabbitMQ | 站内信、微信模板消息的异步投递 | **可选**：相关 Bean 都有 `@ConditionalOnBean(RabbitTemplate)`，没有 MQ 时退回事务提交后的 `@Async` 通知 |

RabbitMQ 做成可选，是 2025-11-13 的事故换来的（`docs/RABBITMQ_INCIDENT_REPORT.md`）：开发机没装 MQ，整个应用启动失败，而 MQ 只承担通知这种非核心功能。

## 备选方案

| 方案 | 为什么没选 |
|---|---|
| 微服务（申请 / 库存 / 通知拆开） | "审批通过"会变成跨服务的分布式事务，需要 Saga 或 TCC 补偿。W3 的并发测试之所以能简单地证明"不超卖、失败整单回滚"，靠的就是**一个本地事务**。1 个人维护多个服务、多套部署，得不偿失 |
| 单体但通知强依赖 MQ | 事故已经证明：非核心依赖不能拖垮核心功能 |
| 不用 Redis，全放 MySQL | 可行，但令牌黑名单、失败计数需要 TTL 自动过期，Redis 更省事；代价是多一个组件 |

## 后果

- ✅ 所有库存变更都在本地事务里，一致性靠数据库保证，容易测试（W3：7 个并发用例）
- ✅ 部署就是一个 docker-compose 文件
- ⚠️ 单点：应用或数据库挂了，全部功能不可用。对一个内部系统可以接受，需要做好备份和重启策略
- ⚠️ 只能纵向扩容。不过定时任务已经用 Redis 分布式锁防重复执行，**需要时可以直接多开几个实例放在 nginx 后面**
- ⚠️ 模块边界只靠包结构约束，容易被随手跨包调用破坏

## 什么时候重新评估

- 有第二个团队要同时改这个系统
- 其他系统（如集团 ERP）需要实时调用库存接口，且调用量明显大于本系统
- 单实例 CPU/连接数成为瓶颈（先加实例，仍不够再考虑拆分）
